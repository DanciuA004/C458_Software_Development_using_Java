# Intermediate Java

## BigDecimal

### 1. Background
The JavaDoc documentation for BigDecimal is pretty technical and can be a bit intimidating. In this section, we present some of the ideas behind BigDecimal and in the next section, we look at some code samples. 

#### 1.1. Immutability

BigDecimal is an immutable type (just like String). That means that a BigDecimal object's value can't be changed once it is set. From a practical standpoint, that means that you must set the result of any BigDecimal operation to another BigDecimal variable. We will see examples of this in the code samples below. 

#### 1.2. Constructors

There are several different constructors that you can use to create instances of BigDecimal. Most of them are pretty straightforward, but we want to discuss two of them here: the String constructor and the double constructor.

It seems intuitive to use a double value to create a BigDecimal instance. After all, they are both decimal numbers, right? Well, the problem with using a double to create a BigDecimal happens because of the imprecise nature of doubles – which is why BigDecimal was created in the first place.  
For example, you would expect that passing in 0.1 to the constructor of BigDecimal would create a BigDecimal with the value of exactly 0.1, but you would be wrong! From the Oracle BigDecimal documentation: 

>The results of this constructor can be somewhat unpredictable. One might assume that writing new BigDecimal(0.1) in Java creates a BigDecimal which is exactly equal to 0.1 (an unscaled value of 1, with a scale of 1), but it is actually equal to 0.1000000000000000055511151231257827021181583404541015625. This is because 0.1 cannot be represented exactly as a double (or, for that matter, as a binary fraction of any finite length). Thus, the value that is being passed in to the constructor is not exactly equal to 0.1, appearances notwithstanding. 

So – it is not a good idea to use this constructor! But what to do if we need to create a BigDecimal with the exact value of 0.1? This is where the String constructor comes in.

It may seem non-intuitive to create a BigDecimal from a String, however, if we pass the String "0.1" into the BigDecimal constructor it will create a BigDecimal equal to exactly 0.1. Again, from the Oracle documentation: 

> The String constructor, on the other hand, is perfectly predictable: writing new BigDecimal("0.1") creates a BigDecimal which is exactly equal to 0.1, as one would expect. Therefore, it is generally recommended that the String constructor be used in preference to this [the double constructor] one. 

Note that none of the other BigDecimal constructors (int, long, BigDecimal) have this problem of imprecision because all of those values can be represented precisely. 

#### 1.3. Precision

An important concept here is precision, which refers to the number of significant digits in a number. In Oracle's example above, 0.1000000000000000055511151231257827021181583404541015625, the only significant digit is the first 1. Everything after the 1 is too small to be significant (except when you are counting money!). So we ignore everything after the 1 and say that the number has a precision of 1 because only one digit is significant.

As a simplified explanation, precision nearly always refers to the number of digits in a number, regardless of how many of those digits are to the left or right of the decimal place.

Each of the numbers below has a precision of 5:

    1.8974
    67.854
    2378.3

#### 1.4. Scale

The scale value is the number of digits to the right of the decimal point. Each of the numbers in the list above has a different scale:

    1.8974: scale = 4
    67.854: scale = 3
    2378.3: scale = 1

When dealing with currency calculations, we will use a scale value of 2. 

#### 1.5. Rounding Modes

The BigDecimal class has several rounding modes. The rounding mode that should be used will be completely dependent on the business rules for your application.  
Different industries and applications have different rules – this is not a decision that should be made by anyone on the development team. Here are the available modes: 

        | Rounding Mode | Description ---------------------------------------------------------------------------- |  
        | CEILING       | Rounds towards positive infinity                                                         |
        | DOWN          | Rounds towards zero                                                                      |
        | FLOOR         | Rounds towards negative infinity                                                         |
        | HALF_DOWN     | Rounds towards the nearest neighbor unless both neighbors are equidistant,               |
                          in which case it rounds down
        | HALF_EVEN     | Rounds towards the nearest neighbor unless both neighbors are equidistant,               |
                          in which case it rounds towards the even neighbor
        | HALF_UP       | Rounds towards the nearest neighbor unless both neighbors are equidistant, in which case |
                          it rounds up                                                                             
        | UNNECESSARY   | Asserts that the requested operation has an exact result so there is no need to round    |
        | UP            | Rounds away from zero                                                                    |

#### 1.6. Considerations

As mentioned above, the scale and rounding modes that are right for your application are completely dependent on your business rules.  
Many times these settings will be related to the generally accepted accounting principles for your particular industry; sometimes tax law determines them. In any case, the development team should never make these decisions! 

### 2. Examples

Now that we have some background information, let's take a look at some code samples. There are additional code samples in the video accompanying this lesson.

In all of the following examples, the comments to the right of the code show the results. 

#### 2.1. String Constructor, Default Scale

In this example, we create a new BigDecimal instance using the string constructor.

        BigDecimal a = new BigDecimal("42.35")

#### 2.2. Setting Scale Without Rounding Mode

In this example, we attempt to create a new BigDecimal object based on `a` but with a scale of 1. This produces an error because we didn't tell the method what rounding mode to use when getting rid of the second digit to the right of the decimal point.

        BigDecimal b = a.setScale(1); //ERROR

#### 2.3. Setting Scale With Rounding Mode HALF_UP

In this example, we add the rounding mode value of HALF_UP when setting the scale to 1. Now BigDecimal knows how to properly round when getting rid of the second digit to the right of the decimal point:

        b = a.setScale(1, RoundingMode.HALF_UP);
        System.out.println(b.toString()); // 42.4

#### 2.4. Setting Scale With Rounding Mode HALF_DOWN

This is the same as the last example except we set the rounding mode to HALF_DOWN instead of HALF_UP. Note the difference in outcome:

        b = a.setScale(1, RoundingMode.HALF_DOWN);
        System.out.println(b.toString()); // 42.3

#### 2.5. Division With No Rounding Mode

In this example, we see that an error is thrown when you attempt to divide two numbers resulting in an infinitely repeating value to the right of the decimal point and you don't set the value for rounding mode:

        op1 = new BigDecimal("10");
        op2 = new BigDecimal("6");
        c = op1.divide(op2); // ERROR

#### 2.6. Division with Various Rounding Modes

In our final example, we see the results of division using three different rounding modes:

        c = op1.divide(op2, RoundingMode.HALF_UP); // 2
        System.out.println(c.toString());
        
        c = op1.divide(op2, 2, RoundingMode.HALF_UP); // 1.67
        System.out.println(c.toString());
        
        c = op1.divide(op2, 2, RoundingMode.DOWN); // 1.66
        System.out.println(c.toString());
