# REST Web Services

## REST API Design

### 1. REST API Components

Before we begin writing code to access our web service we must look at the design of the URLs that will make up the REST API for our Contact List application.

One thing to keep in mind about REST endpoints is that they refer to resources; in other words, they are noun-driven instead of verb-driven. The HTTP verbs tell us what action to take with respect to the resource (noun) specified in the URL. A REST endpoint consists of a URL (specifying a resource) and an HTTP method (specifying the action to take against the specified resource). This means that the URL /book/45 + GET is a different endpoint than /book/45 + DELETE. Even though the URLs are the same, the first one retrieves the book with the ID 45 and the second one deletes the book with ID 45.

Another difference between REST URLs and regular web application URLs is that REST URLs often pass parameters as part of the URL path rather than as form data or request parameters (e.g. ?key=value&key1=value1) although both are acceptable. For example, a URL for retrieving the Contact with id=42 might look like this in a regular web application URL: www.mysite.com/displayContact?contactId=42

The RESTful URL might look like this: www.mysite.com/contact/42

### 2. A Simple REST API

The easiest way to understand a REST API is to walk through the design one. Here, we’ll walk through the design of the Contact List REST API for which we will create a client. In a later section, you will actually implement the server-side portion of this API.

This API is for a simple REST web service that allows users to create, read, update, and delete contacts in a simple contact list application. We will examine each endpoint (URL + HTTP method) along with the required input parameters (RequestBody and path variable or request parameters) and the returned data (ResponseBody).

#### 2.1. Retrieving a Contact

This endpoint takes as input a path variable (contactId) that specifies the contact to be retrieved and returns the requested contact information as a JSON string in the ResponseBody. If the requested contact does not exist, no data is returned.

        HTTP Method: GET
        URL: /contact/{contactId}
        RequestBody: None
        ResponseBody: JSON string containing the requested Contact data

#### 2.2. Creating a Contact

This endpoint takes as input in the RequestBody a JSON string containing the values for the new contact. It returns a JSON string containing all of the original contact data plus a newly assigned contactId issued by the web service. Note that there is no contactId in the path because a contact does not have an id until the web service assigns one.

        HTTP Method: POST
        URL: /contact
        RequestBody: JSON string containing the Contact data
        ResponseBody: JSON string containing all of the original Contact data plus the contactId that the web service assigned to the newly created Contact

#### 2.3. Deleting a Contact

This endpoint takes as input a path variable (contactId) that specifies the contact to be deleted. Notice that the URL is identical to the URL for retrieving a contact but it uses the DELETE method instead of GET. This endpoint returns no data. If the specified contact does not exist, the web service takes no action.

        HTTP Method: DELETE
        URL: /contact/{contactId}
        RequestBody: None
        ResponseBody: None

#### 2.4. Updating a Contact

This endpoint takes as input a path variable (contactId) that specifies the contact to be updated. It also takes as input in the RequestBody a JSON string containing the updated contact information. This endpoint returns no data. There is no reason to return the updated contact information because it will match the contact information passed in. The purpose of this endpoint is to make the persisted contact information look like the contact information sent into the endpoint. Note that this URL is the same as the URL for Create Contact and Delete Contact except that the HTTP method used here is PUT.

        HTTP Method: PUT
        URL: /contact/{contactId}
        RequestBody: JSON string containing the Contact data
        ResponseBody: None

#### 2.5. Retrieving All Contacts

This endpoint takes no input and returns a JSON string representing an array of all the contacts contained in the web service. If there are no contacts contained in the web service, a JSON string containing an empty array is returned.

        HTTP Method: GET
        URL: /contacts
        RequestBody: None
        ResponseBody: A JSON string representing an array of all the contacts contained in the web service.
