# Java Classes and Objects

## Dependency Injection

Dependency injection is the concept that an object should not be responsible for directly instantiating the implementation of any of its member fields that might have more than one implementation.  
In our application, `ClassRosterController` should not be responsible for instantiating a new `ClassRosterDaoFileImpl` object and `ClassRosterView` should not be responsible for instantiating a new `UserIOConsoleImpl` object. With dependency injection, `ClassRosterController` and `ClassRosterView` don't have to make any decisions about which implementation of `ClassRosterDao` or `UserIO` to use — the specific implementation (or dependency) will be handed to (or injected into) these objects when they're created. We do this to ensure that `ClassRosterController` and `ClassRosterView` have no idea which implementation of `ClassRosterDao` or `UserIO` they are using. This makes our components loosely coupled and ensures that they're coupled to the what, not the how, of the other components in the system.

#### 0.1. Why don't we use dependency injection all the time?
If dependency injection and programming to interfaces is such a good thing, why don't we use these techniques in all classes, all the time? The benefit of dependency injection is only realized in cases where there might be more than one implementation of an interface that you can choose from. In these cases, dependency injection gives us an easy mechanism with which to swap implementations without disrupting other parts of the application. For example, we could switch from a file-based `DAO` to a database-based `DAO` and all of the code would still work. Dependency injection doesn't make sense if there is only one implementation of a member field. In that case, there is no chance that we'll ever change implementations because there are no other implementations.

### 1. Constructor Injection

So, we have discussed the concept of dependency injection and its overall benefits. Now it is time to talk about how dependency injection is accomplished. Here, we'll look at constructor injection.  
This just means that we pass in an instance of the dependency to the constructor. The object has no idea what implementation of its dependency was passed in and it doesn't care — that's the point of dependency injection!

### 2. Wiring the Application

Choosing which implementation of a dependency should be used, instantiating that dependency instance, and passing that into the correct constructor is known as wiring the application.  
For right now, that job belongs to the App class. In later sections, we will begin to use the Spring dependency injection container for this, but that is a topic for another day.

The App class acts as the application assembler or architect. It will choose the implementations of the dependencies and wire them together. After everything is properly constructed, the App class hands things off to the controller by calling the run method on the controller.
