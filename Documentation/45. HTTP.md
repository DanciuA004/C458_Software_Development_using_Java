# REST Web Services

## HTTP

HTTP, or Hypertext Transfer Protocol, is a text-based protocol for sending and receiving web content like HTML documents, JavaScript, CSS, images, and video. Its messages are English-like and human readable. Compare this to TCP. TCP is a binary protocol, whose messages are sequences of bits and bytes. Each bit is important, but the bits can't be deciphered with a text editor.

HTTP is sent over TCP. Even though TCP is a binary protocol, it can transmit bytes that contain HTTP's text messages. Ignoring the TCP details, HTTP's behavior is straight-forward: A client sends an HTTP request to a server (both client and server are computers) and the server responds with an HTTP response.

In web services, we want to be able to specify how the server should handle request from the client as well as control what data is sent between the server and the client. HTTP allows web developers to define requests and the server's responses to those requests.

> For web content, the client is most often a web browser like Edge, Firefox, Chrome, or Safari, although mobile applications often use embedded browsers that are built into the application.

### 1. Request

A request is the main function of HTTP, and the HTTP definition includes a limited set of request methods.

The request uses key-value pairs to define what the server should do with the request.

As an example, here's an HTTP request for the Hacker News homepage from a web browser:

        GET / HTTP/1.1
        Host: news.ycombinator.com
        Connection: keep-alive
        Upgrade-Insecure-Requests: 1
        User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_14_0) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/70.0.3538.102 Safari/537.36
        Accept: text/html,application/xhtml+xml,application/xml;q=0.9,image/webp,image/apng,*/*;q=0.8
        Accept-Encoding: gzip, deflate, br
        Accept-Language: en-US,en;q=0.9
        Cookie: __cfduid=dfbe07cb1c609155c811135d7085155561538157611; __unam=3267369-16621568c13-799b9d7d-3

Even with only a casual glance, there are hints about what is being requested and how the browser wants it. The browser may optionally share details about itself. What is the browser asking and what is it sharing?

The general format for an HTTP request is:

        [Request Method] [Path] [Protocol Version]
        [Header Name]: [Header Value]*

The elements of an HTTP request include:

* [Request Method]
  * One of the following values: GET, POST, PUT, DELETE, HEAD, TRACE, OPTIONS, CONNECT, PATH. The value tells the server which action to perform. We'll look at this in more detail later.
* [Path]
  * A relative path (technically, a URI) that identifies the resource being requested. Paths don't have to identify physical files. A resource can be almost anything, from streaming audio to status updates from a video game.
* [Protocol Version]
  * HTTP has more than one version. This value tells the server which version the client prefers. Not all servers support all HTTP versions.
* [Header Name]: [Header Value]*
  * Zero or more header names and values. Each name:value pair is on its own line. Host is almost always included. It identifies the domain being requested. Other headers are optional and are used to negotiate response expectations and behavior.

Examples:

GET is the most common HTTP method. It simply asks the server to send back content from the named host and path without interacting with content on the server at all.

The example below requests content from the URL, http://example.com/admin/index.html, and asks the server to disable caching on the client.
        
        GET /admin/index.html HTTP/1.1
        Host: example.com
        Cache-Control: no-cache

The POST method tells the server it should expect to receive content.

        POST /api/book HTTP/1.1
        Host: example.com
        Content-Type: application/x-www-form-urlencoded

        title=The+Last+Samurai&isbn=978-0811225502&author=Helen+DeWitt

In this example, the content includes attributes of a book. The Content-Type header indicates the content data format.

The DELETE method asks the server to delete an identified resource.

        DELETE /api/book/314 HTTP/1.1
        Host: subdomain.example.com

In this example, the DELETE requests asks the server to delete the resource at URL, http://subdomain.example.com/api/book/314.

Servers are not required to support every possible method, and as web developers, we can assign specific methods to specific resources. For example, we don't want a user to send a DELETE request that would completely remove the content of a web page.

### 2. Response

Hacker News responded to our initial request with this HTTP response:

        HTTP/1.1 200 OK
        Server: nginx
        Date: Thu, 19 Jan 2023 18:44:59 GMT
        Content-Type: text/html; charset=utf-8
        Transfer-Encoding: chunked
        Connection: keep-alive
        Vary: Accept-Encoding
        Cache-Control: private; max-age=0
        X-Frame-Options: DENY
        X-Content-Type-Options: nosniff
        X-XSS-Protection: 1; mode=block
        Referrer-Policy: origin
        Strict-Transport-Security: max-age=31556900
        Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' https://www.google.com/recaptcha/ https://www.gstatic.com/recaptcha/ https://cdnjs.cloudflare.com/; frame-src 'self' https://www.google.com/recaptcha/; style-src 'self' 'unsafe-inline'
        Content-Encoding: gzip
        
        <html op="news">
          <head>
              <title>Hacker News</title>
          ... lots more HTML here.
        </html>

The text that appears above the <html> tag is known as the page headers. This data does not appear to the end user, but the client can use the information to identify specific properties of the page. The content for the user appears inside the <html> element that follows the header.

Again, there's some everyday English in the response header, using key:value pairs. What is it communicating?

The general format for an HTTP response is:

        [Protocol Version] [Status Code] [Status Reason]
        [Header Name]: [Header Value]*
        
        [Content]*

Elements:

* [Protocol Version]
  * The server confirms which version of HTTP it is using. If it's different than the version the client requested, the client must decide how best to handle the response.
* [Status Code]
  * A numeric value between 100 and 599 that indicates how the server handled the request. A 200 status code means that the transfer was successful.
  * Not all requests succeed. Status codes provide feedback when they don't.
* [Status Reason]
  * A phrase describing why the server returned the status code such as: "OK", "Not Found", "Unauthorized", or "Internal Server Error".
* [Header Name]: [Header Value]*
  * Zero or more header names and values. Each name/value is on its own line. Headers are optional but it's common to include Date and Content-Type to help the client make decisions about the content.
* [Content]*
  * Responses commonly include the requested resource as content, though it's not strictly required. Content can be HTML, JSON, JavaScript, CSS, images, and more. Each content type has its own data format.

### 3. URIs and URLs

Technically, HTTP uses URIs (Uniform Resource Identifiers) to identify the requested resource. In the examples above, /admin/index.html and /api/book/314 are URIs in that they specifically identify the resource included in the request. However, a URI like /admin/index.html only works if you know where that resource is stored.

The term URL (Uniform Resource Locator) is much more common and also serves to identify a resource. However, a URL also includes information about where to find the resource and what protocol the server should use the send the data. All parts of the URL are included in the GET request:

        GET /admin/index.html HTTP/1.1
        Host: example.com

The server uses all of this detail to understand what resource is requested, where to find that resource, and what protocol to use. The complete URL for that resource (from the example above) is http://example.com/admin/index.html.

A URL is always a URI in that a complete URL always identifies the resource. A URI may not be a URL if the location and protocol information are not included. However, for practical purposes, most developers simply use URL as the generic term to identify a web resource. For example, we typically refer to a domain name like google.com as a URL, even though it does not include the protocol or the identifier.

### 4. HTTP with JSON

Imagine a kiosk application that allows a customer to order a wood-fired pizza. The customer selects a base pizza, enters their name (to be called for pickup), and adds custom ingredients. The application stores these values in memory. The base pizza is identified by a string code, the customer's name is a string, each of the custom ingredients contains a string name and numeric charge, and the order total is numeric. On completion, the application sends the order to a different application in the kitchen. Because the applications don't share memory, they need a reliable way to communicate. JSON is a good choice.

A JSON representation of the order might look like this:

        {
            "menuItem": "veggie-lover",
            "customer": "Leyla",
            "addOns": [
                { "name": "Extra mozzarella", "price": 1.75 },
                { "name": "Capers", "price": 0.95 }
            ],
            "total": 19.25
        }

JSON works well as a serialization format because it's an open standard. Most general-purpose programming languages have one or more libraries capable of formatting their data in JSON and reading JSON values back. This is especially useful for crossing programming language boundaries. A program written in Python will have no problem sharing data with a program written in Java as long as they communicate with JSON messages. Both the Python and the Java programs will have no problem communicating with a program written in Rust.

JSON becomes more powerful when we combine it with HTTP. We can include our serialized JSON data as request content. Then the recipient can deserialize the content and make decisions about the order.

Here is an HTTP request with JSON content:

        POST /api/order HTTP/1.1
        Host: kitchen.woodfired.com
        Content-Type: application/json
        
        {
            "menuItem": "veggie-lover",
            "customer": "Leyla",
            "addOns": [
                { "name": "Extra mozzarella", "price": 1.75 },
                { "name": "Capers", "price": 0.95 }
            ],
            "total": 13.25
        }
