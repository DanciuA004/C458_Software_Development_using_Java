# Relational Databases and MySQL

## Entity Relationship Diagrams

### 1. Using ERDs

When discussing an abstract form of a database, we typically use the term entity to reference each object (such as people, things, places, and events) that we want to manage in a database, and we use entity relationship diagrams (ERDs) to represent the entities and the relationships between the entities. Because each final version of an entity will be a table in the completed database, we often use the terms entity and table to mean virtually the same thing, where entity is an abstract representation of the same thing described by a table in a database.

The normalization steps described elsewhere in the course help us identify what tables and fields the database will have, and how the tables themselves are related to each other. At the end of that process, however, you should create an ERD, a visual representation of the database structure that gives us the following advantages:

- It helps identify places where the proposed structure may not work. While normalization should help you identify exactly how the tables are related to each other, you may discover while building the ERD either that one or more tables aren't related to any of the other tables or that some of the relationships don't make sense when you try to map them to the normalized tables. Identifying these problems in the design phase will help avoid problems that might otherwise appear in the SQL scripts used to define the database.
- It allows the team to see the database's structure, which helps each team member quickly identify what fields are in which tables and how the tables are related. 
- It gives you a single, condensed representation of the structure, which helps you write SQL statements more quickly, especially when the SQL statement references two or more tables.

Essentially, at the end of the normalization process, you have a description of the tables and fields you need to include in the database, kind of like the description of a house for sale on a realtor's web page. The description tells you what rooms are in the house and a general idea of how the house is laid out (how many floors, whether there is a basement or a garage, and so on), but having a floor plan of the house lets you see exactly how the rooms are connected to each other and how much space each room has. An ERD is the equivalent of a floor plan or blueprint of the database.

For this example, we will use a ContactList database that includes the following tables:

- Contact: Stores the names of people in our contact list 
- Phone: Stores the phone numbers associated with our contacts, allowing us to associate multiple phone numbers with each individual 
- PhoneType: Stores information about the types of phone number the database, to distinguish between home numbers, work numbers, cell phone numbers, and so on.

#### 1.1. Available Tools

Because one of the main purposes of an ERD is to ensure that the database structure is correct, you should make sure that whatever tool you use will allow you to make changes to the structure at any point.

One of the easiest tools to use, at least for the first couple of drafts, is pencil and paper. Starting with pencil and paper allows you to sketch out the design easily, as well as update the sketches as you find problems with the structure or ways to make it more efficient.

Once you have a sketch draft of the ERD, you can use a computer-based tool to create a digital version of the ERD that you can save with the database documentation and share with team members. Most tools designed to create flowcharts and wireframes can also create ERDs, so chances are good that you already have something on your computer that you can use for this purpose. Suggestions include:

- Draw.io: A free, Chrome-based tool that is completely free to use and that allows you to save files to the cloud (Google Drive or OneDrive, primarily) or to your computer. Draw.io has a set of database-specific shapes that streamline the design process, and there is a desktop app if you prefer to install the application locally.
- ERDPlus: Another free, web-based tool designed specifically for ERDs and similar database structures.

You may already have a design program that you use for wireframes and sitemaps and if that tool also supports ERDs, feel free to use it. The focus here should be on building accurate ERDs, not on the tools you use to build them.

### 2. ERD Components

A well-designed ERD includes all of the following information:

- The tables required by the database, including the name of each table 
- A list of fields contained in each table 
- Metadata about each field, including the name of the field, its data type, and whether or not it is nullable 
- Identification of all primary and foreign key fields 
- How each table is related to each other

In addition, a more detailed ERD may contain information about indexes, how the keys are named, and details about the cardinality of each relationship, but for now, we'll focus on the basics.

> Note  
> An ERD never includes data – just a description of the kind of data that the table will hold. That said, it is often useful to have access to sample data sets, to help you identify what fields the ERD should include and what the appropriate data type is for each field.

This is also the step where you want to define naming conventions and ensure that they are used across all objects. There is a lot of flexibility in naming things in a database and establishing a naming convention helps avoid coding problems down the road. Remember that while SQL is not typically case-sensitive on its own, the programming languages you will use with SQL (such as C# or Java) probably are. The examples here use CamelCase, with each word capitalized but not separated, but that is only one option in the real world.

Another part of the naming convention is the use of singular versus plural nouns, especially for table names. In this example, we will use singular nouns in table names.

#### 2.1. Tables

A table is represented by a rectangle, normally divided into three sections horizontally. The ERD normally includes the name of the table in the topmost section (like a title), the primary key field(s) in the next section down, and the remaining fields are added to the bottommost section.

As an example, when we normalized a contact list data set, we identified a table that represents the contacts themselves. We named the table Contact, and we determined that we need a surrogate key – a value that is created specifically to identify individual records in a table – so we need to include ContactID as the table's primary key. In addition, we have fields for other kinds of information we want to associate with each contact, such as their name and their address.

#### 2.2. Fields

We included a basic list of fields in the table, but a well-designed ERD includes more information about each field beyond the name. For example, we need to know which fields are nullable and what data type each field will use.

> The concept of null is covered in more detail elsewhere in the course, but the essential concept is that a field can be required or nullable. This is a business rule that determines whether a field must have a value or if it can be left empty.

To include this information, we will format each required (non-nullable) field in bold and add the data type to the right of the field name. Let's walk through the choices in our Contact table and then add that to the ERD.

- ContactID: This is a surrogate key that is required. We will use INT as the data type for this field. 
- FirstName and LastName: Both fields are required, and both are strings. Because they are not a fixed length, we will use VARCHAR as the data type for these fields, with a limit of 25 characters for the first name and 50 characters for the last name. 
- Address: We will add phone number information elsewhere in our database, so we don't necessarily need address information. Like FirstName and LastName, the field will contain strings of varying lengths, so we will use VARCHAR with a maximum length of 100 characters.

The ERD for this table now looks like: 

![Diagram of table with field sizes next to the field names](/images/erd-02.png)

At this stage, be sure not to confuse values with fields. Each field name should be a description of the data the field will store, rather than values that will be included as data. For example, if we wanted to include a salutation (like Mr., Ms., Dr., and so on), we would use a single field named Salutation that could hold at most one of those values, rather than creating a separate field for each potential salutation.

Also note that different RDBMSs use data types somewhat differently, so the exact data type you assign to each field will depend on whether you are using MySQL, SQL Server, or something else. We will use relatively generic types here, but an ERD for a specific RDBMS may need more details.

#### 2.3. Keys

A final addition at the table level is to indicate the primary and foreign keys. This is often done by adding PK or FK (respectively) to the left of the appropriate field names in the table. It is also common to underline the primary key field (or any other field whose value must be unique within the table), to help make it even more visible.

In this case, our table has only one field in the primary key and no foreign keys, so the additional notation will add PK to the left of ContactID and underline the field name.

With the key notation, the Contact table now looks like:

#### 2.4. Additional Tables

Now look at the ERD representations of the other two tables in our Contacts database. What can you tell about the fields in each table?

The PhoneType table allows us to store information about the different kinds of phones our contacts might use so that we can identify separate work numbers, cell phone numbers, home numbers, and fax numbers for each contact. It uses PhoneTypeID as the primary key, with the INT data type, while PhoneType will be VARCHAR(10). Both fields are required.

![PhoneType table with PhoneTypeID as the PK and a second field named PhoneTypeName](/images/erd-04.png)

The phone numbers themselves are recorded in a separate Phone table, using PhoneID INT as the primary key, PhoneNumber CHAR(10), and foreign keys PhoneNumberTypeID and ContactID.

![Phone table with PK PhoneID INT, PhoneNumber CHAR(10), FK PhoneTypeID INT, and FK ContactID INT](/images/erd-05.png)

Note especially that we treat the phone number itself as a string, rather than as a number. We do this for multiple reasons:

- We aren't going to perform mathematical operations with phone numbers, so we don't need to store them as numbers. 
- Phone numbers can contain non-numeric characters, such as letters or dashes, especially if we have contacts outside the United States. 
- Storing the data as a CHAR field requires less storage than a 10-digit INT field, and the smaller field size will help speed up database interactions.

You will notice, too, that the Phone table includes two fields designated as foreign keys (FK): PhoneTypeID and ContactID. This is one way that we can use an ERD to represent relationships between tables, but let's look at a more formalized representation.

#### 2.5. Relationships

So far, we have seen representations of individual tables, but that's kind of like looking at a blueprint that only shows the individual rooms. We need to see how the pieces fit together, so we need to add visualizations for the relationships themselves. We'll start with the Contact and Phone tables.

While there is variation in techniques used to represent the relationship between two tables, the simplest is to use an arrow that points FROM the one side of the relationship TO the many side of the relationship. In this case, each contact can have many phone numbers, but each phone number is associated with exactly one contact, so the arrow points from Contact to Phone.

![The Contact and Phone tables as shown before, with an arrow connecting ContactID in the Contact table to ContactID in the Phone table](/images/erd-06.png)

However, we can add notations to provide more details about the relationship.

![The same diagram, but the line has a small vertical cross line on the Contact side and a crow's foot notation on the Phone side.](/images/erd-07.png)

In this case, we have added a crow's foot marking (three small lines replacing the arrowhead) on the many side of the relationship to indicate that any record in the Contact table can be associated with several records in the Phone table. In addition, there is a small vertical line on the Contact side to indicate that each record in the Contact table must have at least one related record in the Phone table. This supports the business rules for the database which state that we must have at least one phone number for each contact.

Now look at the relationship between Phone and PhoneType.

![The Phone and PhoneType tables. A line connects them with a crow's foot on the Phone side but no additional notation on the PhoneType side.](/images/erd-08.png)

In this case, each PhoneType can be associated with any number of phone numbers, but each phone number must have exactly one type, so the crow's foot appears on the Phone table (the many side of the relationship). Here, though, we exclude the vertical line on the PhoneType side. It's quite possible that when we set up the database, we might include phone types that may never be used (like fax numbers), so we don't want to force each PhoneType to be used if it isn't necessary.

Notice how this view allows us to see all fields in all tables in a single view, as well as identify how the tables are connected to each other. When we write SQL statements to retrieve data from the database, knowing what field is in what table is critical, as is understanding the relationships (or JOINs) between the tables. #### 3.1. What About Many-to-Many Relationships?

When we start with an unnormalized set of data, we will typically identify several many-to-many relationships between tables as we normalize the data into the required tables. However, in a normalized database (normalized to at least 2NF), all relationships will be either one-to-one relationships (where each record in one of the tables corresponds to at most one record in the other table) or more often, one-to-many relationships. Any many-to-many relationships will be defined as two one-to-many relationships between three tables, using a bridge table to connect the original tables.

A many-to-many relationship, then, must include three separate tables: the two original tables and a bridge table. In many cases (but not all), the primary key fields of the original tables are used to create the primary key of the bridge table, in which case we have multiple fields that are both a foreign key and part of the primary key.

As an example, in a typical school database, there is a many-to-many relationship between students and classes, because each student is likely to take multiple classes (over time, if not simultaneously), and each class should include multiple students.

Here is a basic example of what this relationship might like in an ERD:

![Diagram with tables for Student, Enrollment, and Class. Student includes PK StudentID, Enrollment includes PK FK1 StudentID and PK FK2 ClassID, and Class includes PK ClassID.](/images/erd-10.png)
The Enrollment table here works as a bridge table between Student and Class, and its primary key is a composite key that includes both the StudentID and the ClassID fields. Each of those fields individually is a foreign key field that defines the relationship with the original tables.

In use, each student can appear as many times as necessary in the enrollment table, to represent each course they take. Similarly, each class can appear in the enrollment table as many times as necessary for each student who enrolls in the class. However, the composite key that includes both StudentID and ClassID means that no student can be enrolled in the same class more than once.
