# REST Web Services

## REST

REST, or Representational State Transfer, is a software architecture for web services. It uses HTTP to fetch data and execute actions. It's not a protocol and, to be honest, not even a true standard. Roy Fielding defined REST in his Ph.D. thesis. The thesis outlines several principles for REST architecture including statelessness (REST shouldn't rely on what just happened to decide what to do next) and cache-ability (if we ask for the same data twice, the server may suggest we use what we already have). The principles are a bit academic. They serve more as guidance than formal rules.

Still, there are a few generally-accepted patterns classified as "REST" in the development community. There's more than one way to build a REST API, but architectures include the features described below.

### 1. CRUD

A REST resource can be any logical chunk of data: customers, shipping containers, chess moves... anything. A REST API exposes some set of CRUD (create, read, update, and delete) operations that act on each resource. It's possible to expose non-CRUD operations – maybe an action kicks off a background process, so there's nothing limiting REST to CRUD. But generally, each resource exposes one or more of the CRUD operations. 

### 2. HTTP Methods

A REST request is simply an HTTP request. It uses one of five HTTP methods to determine which CRUD operation to activate.

* GET
  * A read operation, may return a single item or multiple items
* POST
  * A create operation, includes data to be added to some data store
* PUT
  * Update, in some cases a full versus partial update
* PATCH
  * Update, in some cases partial versus full update
* DELETE
  * The delete operation

### 3. HTTP Status Codes

The server may respond to each request with a rich set of status codes to more thoroughly explain the outcome. Examples:

* 200 OK
  * A successful read, should include the requested resource
* 201 Created
  * Successful create, could include the newly-created resource or a URL to fetch it
* 204 No Content
  * A successful update or delete operation that doesn't require a resource to be returned
* 404 Not Found
  * The server could not find the requested resource.
* 405 Method Not Allowed
  * Indicates the requested HTTP method is not supported. Servers are not required to support every HTTP method.
* 409 Conflict
  * Someone else updated or deleted the resource since you last fetched it.

For a complete list of available HTTP status codes, see MDN's page, HTTP response status codes

### 4. URLs

REST resources are identified by URL. Conventions differ, but the following are common.

        URL                 Resource
        /api/contact        All contacts (opinions differ) or creates a contact with the POST method
        /api/contacts       All contacts (opinions differ)
        /api/contact/314    A single contact with the identifier 314
        /api/sandwich/622   A single sandwich with the identifier 622

In this example, /api/ represents a relative path to the requested resource, starting from the server address identified elsewhere in the request.

The content after /api/ is called an endpoint, and it references the type of data the complete URL will retrieve.

As an example, there is a working API at http://contactlist.us-east-1.elasticbeanstalk.com. By itself, the URL opens a web page with some basic information about the API, but if we add the endpoint contacts, http://contactlist.us-east-1.elasticbeanstalk.com/contacts , the URL returns a list of contacts in the current dataset.

We can add an endpoint with a contactId value to return that specific contact, like http://contactlist.us-east-1.elasticbeanstalk.com/contact/2 .

Check each of the URLs above to see how the results differ. If they don't work, contact an instructor for assistance.

### 5. Serialization

Serialization is the process of streaming (sending and receiving) data in a format that can be stored in a file or in a data buffer.

REST doesn't specify the serialization format to be used for fetching and submitting data. Both XML and JSON are common. JSON's advantages include a smaller payload and easy conversion to JavaScript. That's why we use JSON rather than XML in this course.

Some servers allow the client to choose a serialization format using the Accept HTTP header. The value application/xml returns XML and application/json returns JSON.

It's also important to tell the server which format is used in the request. We specify using the Content-Type HTTP header. The value application/x-www-form-urlencoded tells the server to expect standard HTML form data, while application/json indicates a JSON payload.
