# REST Web Services

## JDBC Template

### 1. Overview

JDBC Template is the Spring way of using JDBC to communicate with the database. It abstracts away some of the work we need to do with JDBC so that we can more quickly and easily develop our database applications.

JDBC is the fundamental technology underneath JDBC Template, which means we will still need our specific JDBC Driver for the database we are working with. We will add in one additional dependency for the JDBC Template code itself.

### 2. JDBC Template and Spring Boot

The specific version of JDBC Template we are going to use comes from Spring Boot. Spring Boot is a relatively recent addition to the Spring ecosystem and it allows us to develop Spring web applications without having to worry about doing too much configuration. A lot of the common settings are assumed, but we also have the ability to override them if necessary. We will look at Spring Boot in more detail in a future lesson, but for now, be aware that much of the configuration work is being handled behind the scenes for us.

### 3. JDBC versus JDBC Template

#### 3.1. Making a Connection

With JDBC we had to define our connection in code. You may remember this method that we had to create in the code-along:

        private static DataSource getDataSource() throws SQLException {
            MysqlDataSource ds = new MysqlDataSource();
            ds.setServerName("localhost");
            ds.setDatabaseName("todoDB");
            ds.setUser("root");
            ds.setPassword("rootroot");
            ds.setServerTimezone("America/Chicago");
            ds.setUseSSL(false);
            ds.setAllowPublicKeyRetrieval(true);
    
            return ds;
        }

With JDBC Template, we define these values in a properties file located in the 'resources' directory of our project. Spring Boot uses properties files for any additional configuration that is necessary, and when we connect to a database, we must define the location of that database. An example of what that looks like is here:

        spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver
        spring.datasource.url=jdbc:mysql://localhost:3306/todoDB?serverTimezone=America/Chicago&useSSL=false
        spring.datasource.username=root
        spring.datasource.password=rootroot

With these in place we can hook in our JdbcTemplate object by autowiring it into the class we want to use it in:

        @Autowired
        private JdbcTemplate jdbc;

Behind the scenes, Spring will look up the spring.datasource information in the program's properties file and instantiate the JdbcTemplate for us. Now we are ready to use it to talk to the database.

#### 3.2. Querying the Database

When we query the database from the JDBC side, we have to define our Statement or PreparedStatement, fill it with data, and then process the ResultSet to get information back. We can choose to put the data into an actual object or not depending on our need. For example, here is our "displayList" method in JDBC:

        Statement stmt = conn.createStatement();
        ResultSet rs = stmt.executeQuery("SELECT * FROM todo");
        while (rs.next()) {
            System.out.printf("%s: %s -- %s -- %s\n",
                    rs.getString("id"),
                    rs.getString("todo"),
                    rs.getString("note"),
                    rs.getBoolean("finished"));
        }
        System.out.println("");

With JDBC Template this changes up a bit. To start with, we don't build a Statement or PreparedStatement; instead, we pass our query directly into the method we use to make the call with question marks defining any parameters we need to give the query. We then define a RowMapper that will change the ResultSet directly into the object we are working with.

RowMapper is an interface that we implement in a mapper class for the specific object we want to process. Its entire job is to take one row of the ResultSet and return an object built from that row.

After we pass in the RowMapper, we then give the method the parameters for the query in the order they need to be inserted into the query.

The same bit of code from up above looks like this when we use JDBC Template:

        List<ToDo> todos = jdbc.query("SELECT * FROM todo", new ToDoMapper());
        for (ToDo td : todos) {
            System.out.printf("%s: %s -- %s -- %s\n",
                    td.getId(),
                    td.getTodo(),
                    td.getNote(),
                    td.isFinished());
        }
        System.out.println("");

Processing a list of objects ends up being a lot cleaner to work with then processing a ResultSet, and the JDBC Template helps us do that.

#### 3.3. RowMapper

We use RowMapper to turn a row of the ResultSet into an object. An example RowMapper for a ToDo item looks like this:

    private static final class ToDoMapper implements RowMapper<ToDo> {

        @Override
        public ToDo mapRow(ResultSet rs, int index) throws SQLException {
            ToDo td = new ToDo();
            td.setId(rs.getInt("id"));
            td.setTodo(rs.getString("todo"));
            td.setNote(rs.getString("note"));
            td.setFinished(rs.getBoolean("finished"));
            return td;
        }
    }

By implementing the RowMapper interface, we get this mapRow method, and by specifying the type "<ToDo>", we let it know what mapRow should return. Inside this method, we are only looking at a single row of the ResultSet, so we can immediately pull the data out of it and create our new object.

When using the RowMapper, be sure to import:

        import org.springframework.jdbc.core.RowMapper;

There is another RowMapper related to the Swing UI packages that can get imported by mistake if you aren't careful.

By using the RowMapper, JDBC Template helps us avoid writing a bunch of repetitive code that loops through the ResultSet, creating objects and putting them into Lists.

### 4. Implementation

Download the start project here: JDBCTemplateExampleStarter.zip

This project will mirror the JDBC project so that you can see the differences first hand between JDBC and JDBC Template in a simple project. We will use the same database, so if you no longer have that database created, go back to the previous lesson and run the SQL script again.

This project starts out with some extra stuff in order to get moving a little quicker. Your pom.xml should already have the two necessary dependencies in it:

        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-jdbc</artifactId>
            <version>2.0.5.RELEASE</version>
        </dependency>
        <dependency>
            <groupId>mysql</groupId>
            <artifactId>mysql-connector-java</artifactId>
            <version>8.0.13</version>
        </dependency>

You can see the MySQL driver is still in there, but we've added the Spring Boot JDBC dependency as well. This is what gives us the JDBC Template and other Spring Boot features we will be using.

You should also note that the App class is annotated as a @SpringBootApplication and implements a CommandLineRunner interface. This is how we set up a console Spring Boot application. By implementing that CommandLineRunner class, we must add in the "run" method and use that to start up our program from the "main" method.

#### 4.1. Database Connection

We will start by setting up our database connection, and the first step is to set up our properties file. In your "src/main/resources" folder or "Other Sources" section of the Project tab, create an empty file named "application.properties". This name needs to be exact because that is what Spring Boot is expecting to see. Inside the file, we will add several lines that are key-value pairs:

        spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver
        spring.datasource.url=jdbc:mysql://localhost:3306/todoDB?serverTimezone=America/Chicago&useSSL=false
        spring.datasource.username=root
        spring.datasource.password=rootroot
        
        logging.pattern.console=

* driver-class-name is the specific name of the JDBC driver we are using.
* url is the location of the database as well as any additional parameters we can't pass through other properties.
* username and password are the login credentials for your MySQL database.
* pattern.console we are using specifically for this project to suppress Spring Boot console output so we only see our own output. We typically wouldn't use this property but it helps our small project work a little better.

Now that we have these set up we can go into the App class and add in the lines:

        @Autowired
        private JdbcTemplate jdbc;

Behind the scenes, Spring has created the JdbcTemplate bean for us using the properties we defined. The @Autowired annotation asks Spring to give us that bean so we can use it in our App class.

Now that we have the JdbcTemplate object, we can start talking to the database, but before we write any queries, we should set up our RowMapper.

#### 4.2. ToDoMapper

We are going to create our mapper as a private internal class of the App class. This means it will only be accessible from the App class but we are okay with that – that's the only place that ever needs it. We see this pattern with mappers: creating them as internal classes to tie them directly to the class that is primarily using them.

This is the mapper we are going to add to the bottom of the App file:

    private static final class ToDoMapper implements RowMapper<ToDo> {

        @Override
        public ToDo mapRow(ResultSet rs, int index) throws SQLException {
            ToDo td = new ToDo();
            td.setId(rs.getInt("id"));
            td.setTodo(rs.getString("todo"));
            td.setNote(rs.getString("note"));
            td.setFinished(rs.getBoolean("finished"));
            return td;
        }
    }

* We declare this as a private static final class so that it is only accessible from this class and it can't be changed or re-overridden in any way.
* When we implement the RowMapper, we have to add in the <ToDo> generic so that it knows which object type we are processing.
* The only overridden method we have to implement is the mapRow method, which will return the object we indicated with the generic above.
* Inside the mapper, we create one instance of the object from fields in the ResultSet. The field names must match what we are getting from the database.

With the mapper in place, we can start filling in our methods, starting with "displayList".

#### 4.3. DisplayList

We can now fill in the "displayList" method with the following code:

    private void displayList() throws SQLException {
        List<ToDo> todos = jdbc.query("SELECT * FROM todo", new ToDoMapper());
        for (ToDo td : todos) {
            System.out.printf("%s: %s -- %s -- %s\n",
                    td.getId(),
                    td.getTodo(),
                    td.getNote(),
                    td.isFinished());
        }
        System.out.println("");
    }

* We start by declaring a List of the objects we are getting and then use our JdbcTemplate object to query the database.
* The query method expects us to give it at least a String SQL query and a mapper: in this case, our ToDoMapper.
* If we had additional parameters for our query, those would be added in after the ToDoMapper.
* Once we have our results in the List of ToDo items, we can loop over it and print out each item. The ToDoMapper will have filled in all the data in the object so we don't have to worry about any missing data.

You should be able to run the program and see the existing entries in the database, next we'll look at adding in an item.

#### 4.4. AddItem

The procedure for adding an item starts out similar to JDBC where we ask for the ToDo information, but changes when we need to talk to the database. Here is the code:

    private void addItem() throws SQLException {
        System.out.println("Add Item");
        System.out.println("What is the task?");
        String task = sc.nextLine();
        System.out.println("Any additional notes?");
        String note = sc.nextLine();

        jdbc.update("INSERT INTO todo(todo, note) VALUES(?,?)", task, note);
        System.out.println("Add Complete");
    }

* We use the JdbcTemplate method "update" to make changes in the database, this means INSERT, UPDATE and DELETE calls all go through the "update" method.
* We first have to put in our SQL query with question marks for the parameters we got for the user and then add in those variables.
* We don't need a mapper in this case because we are not expecting results back from the INSERT.

This should allow you to now add in new entries and view them with the "displayList" method.

Next, we will look at the "updateItem" method.

#### 4.5. UpdateItem

The "updateItem" method is a little longer than the others so we are going to look at it in a few chunks, let's first start with retrieving the object we are updating:

        System.out.println("Update Item");
        System.out.println("Which item do you want to update?");
        String itemId = sc.nextLine();
        ToDo item = jdbc.queryForObject("SELECT * FROM todo WHERE id = ?", new ToDoMapper(), itemId);

* We still start out asking for the ID just as we did with JDBC.
* Once we have the ID we can use the "queryForObject" method in JdbcTemplate to retrieve a single object from the database.
  * If for some reason we get no object or multiple objects back from the queryForObject, an Exception will be thrown.
* We add in the SQL Query with a question mark for our ID parameter, indicate the mapper to use, and then add in our itemId to fill in the question mark.
* This call is saved back into a ToDo item with all of its data filled in so we can use it later.

The next chunk displays the current item and asks what to update, making the changes we ask it to:

        System.out.println("1. ToDo - " + item.getTodo());
        System.out.println("2. Note - " + item.getNote());
        System.out.println("3. Finished - " + item.isFinished());
        System.out.println("What would you like to change?");
        String choice = sc.nextLine();
        switch (choice) {
            case "1":
                System.out.println("Enter new ToDo:");
                String todo = sc.nextLine();
                item.setTodo(todo);
                break;
            case "2":
                System.out.println("Enter new Note:");
                String note = sc.nextLine();
                item.setNote(note);
                break;
            case "3":
                System.out.println("Toggling Finished to " + !item.isFinished());
                item.setFinished(!item.isFinished());
                break;
            default:
                System.out.println("No change made");
                return;
        }

The last chunk makes the actual call to the database to update the row:

        jdbc.update("UPDATE todo SET todo = ?, note = ?, finished = ? WHERE id = ?",
                item.getTodo(),
                item.getNote(),
                item.isFinished(),
                item.getId());
        System.out.println("Update Complete");

* We use the "update" method again here since we are changing the database.
* Our UPDATE query goes in with question marks for all the data we received from the user. We don't necessarily know which field was updated but it is safe for us to just update all of them: the old data will just overwrite itself if there wasn't a change.
* After the UPDATE query, we add in the data to match up with the question marks.

This should allow you to update any existing entry in the database.

Lastly, we will take a look at removing an item from the database.

#### 4.6. RemoveItem

Removing an item is much simpler than updating an item:

    private void removeItem() throws SQLException {
        System.out.println("Remove Item");
        System.out.println("Which item would you like to remove?");
        String itemId = sc.nextLine();
        jdbc.update("DELETE FROM todo WHERE id = ?", itemId);
        System.out.println("Remove Complete");
    }

* We start out getting the ID for the item we want to delete.
* Once we have the ID we can use the JdbcTemplate "update" method to perform the delete.
* The DELETE query is put in place with a question mark to be replaced by the ID we asked the user for.
* We add in our itemId to fill in the question mark.

All functionality should be in place and the ToDo Item List program should be complete.
